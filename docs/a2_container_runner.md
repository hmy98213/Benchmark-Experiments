# A2 In-Container Runner

This guide is for the internal A2 server case where you are already inside a
container that has vLLM Ascend installed. The runner does not start Docker. It
directly runs:

```bash
vllm serve ...
vllm bench serve ...
```

For most selected `model x dataset x method` combinations, the runner starts a
fresh vLLM server, runs one benchmark, stops that server, then starts the next
case. Methods can optionally define multiple `bench_passes`; those passes run
back-to-back against the same server process.

## Step 1. Enter The Ascend Container

Do this on the internal A2 server. The exact command depends on how the
container is started there. Once inside the container, these commands should
work:

```bash
which vllm
python3 -m pip show vllm | head
npu-smi info
```

If `which vllm` prints nothing, set `VLLM_BIN` later in the YAML config.

## Step 2. Get The Repo

Clone the runner branch inside the container:

```bash
git clone -b codex/a2-container-runner https://github.com/hmy98213/Benchmark-Experiments.git ~/suffix-bench
cd ~/suffix-bench
```

If the repo already exists:

```bash
cd ~/suffix-bench
git fetch origin codex/a2-container-runner
git checkout codex/a2-container-runner
git pull --ff-only
```

The repo also includes the longer benchmark data files used by non-smoke runs:

```bash
ls -lh data/datastores/datastores_mixed_custom.jsonl
ls -lh data/spec_bench/question.jsonl
```

The current default YAML is a short `random3` smoke test, so it does not need
these data files.

## Step 3. Edit The Experiment Config

For the current random3 smoke test, edit:

```bash
vi configs/a2_random3_smoke.yaml
```

The three most important fields are at the top. The current smoke config is:

```yaml
models:
  - qwen35_27b_w8a8_mtp
  - qwen36_35b_a3b
  - qwen3_next_80b_a3b_instruct

datasets:
  - random3

methods:
  - baseline
  - ngram
  - suffix
  - mtp
  - mtp_ngram_concat
  - mtp_suffix_concat
```

The runner executes the selected models and datasets. Methods come from the
top-level `methods` list unless a model entry has its own `methods` list:

```text
each selected model x each selected dataset x that model's selected methods
```

The current smoke config runs 3 models and `random3`.
`Qwen3.5-27B-w8a8-mtp` runs the full A2-supported method set. The other two
models start with model-free methods only until their MTP support is confirmed.
`suffix` and `mtp_suffix_concat` run two bench passes against the same server
process:

```yaml
models: [qwen35_27b_w8a8_mtp, qwen36_35b_a3b, qwen3_next_80b_a3b_instruct]
datasets: [random3]
methods: [baseline, ngram, suffix, mtp, mtp_ngram_concat, mtp_suffix_concat]
```

DFlash is not included in this A2 smoke matrix because the current vLLM Ascend
stack does not support `method=dflash`.

The warm-start rows are named `suffix_cold`, `suffix_warm`,
`mtp_suffix_concat_cold`, and `mtp_suffix_concat_warm` in `summary.csv`, when
those methods are selected for a model.

## Step 4. Set Model Paths And TP/DP

Model weights are not stored in GitHub. Put the models on the internal server,
then point `model_catalog` to those paths.

The current default smoke config is already set to these 8-NPU model paths:

```yaml
TP: 8
DP: 1
NPU_DEVICES: "0,1,2,3,4,5,6,7"

model_catalog:
  qwen35_27b_w8a8_mtp:
    path: /models/Qwen3.5-27B-w8a8-mtp
    served_model_name: qwen3.5-27b-w8a8-mtp

  qwen36_35b_a3b:
    path: /models/Qwen3.6-35B-A3B
    served_model_name: qwen3.6-35b-a3b
    methods:
      - baseline
      - ngram
      - suffix

  qwen3_next_80b_a3b_instruct:
    path: /models/Qwen3-Next-80B-A3B-Instruct
    served_model_name: qwen3-next-80b-a3b-instruct
    methods:
      - baseline
      - ngram
      - suffix
```

Top-level `TP`, `DP`, and `NPU_DEVICES` are defaults. A model entry can override
them with `tp`, `dp`, and `npu_devices`. A model entry can also override the
top-level method list with `methods`.

## Step 5. Choose Datasets

The default config has these dataset keys:

```yaml
datasets:
  - random3
  - random64
  - prefixrep64
  - datastores384
  - specbench100
```

`random3`, `random64`, and `prefixrep64` are generated by `vllm bench` and need
no data file.

The default config currently selects `random3`, a quick smoke dataset with
3 prompts, 256 input tokens, and 32 output tokens. `datastores384` uses:

```bash
data/datastores/datastores_mixed_custom.jsonl
```

`specbench100` uses:

```bash
data/spec_bench/question.jsonl
```

Both paths are relative to the repo root, so the repo can be cloned under
`~/suffix-bench`, `/workspace/suffix-bench`, or another directory.

## Step 6. Choose Methods

The top-level default method keys are:

```yaml
methods:
  - baseline
  - mtp
  - ngram
  - suffix
  - mtp_ngram_concat
  - mtp_suffix_concat
```

These are the full smoke-test methods supported by the current hybrid vLLM
patch. The current smoke config lets the MTP model use the full list and gives
non-MTP models a model-level override for `baseline`, `ngram`, and `suffix`.
For a model without native MTP support, remove `mtp`,
`mtp_ngram_concat`, and `mtp_suffix_concat`, or add a model-level override:

`dflash` is intentionally omitted for A2 because earlier attempts failed during
server initialization in vLLM Ascend.

```yaml
model_catalog:
  non_mtp_model:
    methods:
      - baseline
      - ngram
      - suffix
```

They map to `method_catalog`:

```yaml
method_catalog:
  baseline: null

  mtp:
    method: mtp
    num_speculative_tokens: 4

  ngram:
    method: ngram
    num_speculative_tokens: 4

  suffix:
    method: suffix
    num_speculative_tokens: 4
    bench_passes: [cold, warm]

  mtp_suffix_concat:
    method: mtp_suffix_concat
    num_speculative_tokens: 4
    hybrid_mtp_tokens: 1
    bench_passes: [cold, warm]
```

To change draft length, edit `num_speculative_tokens`. For hybrid methods,
`hybrid_mtp_tokens` controls how many draft tokens come from MTP before
ngram/suffix continues the draft. In this smoke config, all speculative methods
have a total draft budget of `num_speculative_tokens: 4`; hybrid keeps
`hybrid_mtp_tokens: 1` because that is the MTP segment split, not the total
draft budget.

`bench_passes: [cold, warm]` means the runner starts vLLM once, runs `vllm bench`
once for the cold row, then runs `vllm bench` again for the warm row without
restarting vLLM. The suffix tree is expected to persist only within that server
process. If cold and warm metrics are exactly identical, inspect the shared
`server_log` path in `summary.csv`; identical metrics usually mean the warm pass
did not benefit from retained suffix history or the model/software stack reset
that state internally.

## Step 7. Run Checks Before The Real Experiment

Run the local control-flow self-test:

```bash
python3 scripts/test_a2_container_runner.py
```

Check the selected config without starting vLLM:

```bash
bash run.sh --preflight
```

Print the exact `vllm serve` and `vllm bench serve` commands without running
them:

```bash
bash run.sh --dry-run
```

Dry-run only prints commands. It does not create `results/` directories and does
not write `metadata.json`.

If you use a different config file:

```bash
bash run.sh configs/my_experiment.yaml --preflight
bash run.sh configs/my_experiment.yaml --dry-run
```

For the current random3 smoke test, you can also use the dedicated wrapper:

```bash
bash run_a2_random3_smoke.sh --help
bash run_a2_random3_smoke.sh --dry-run
bash run_a2_random3_smoke.sh --tp 6 --npu-devices 2,3,4,5,6,7 --dry-run
```

The wrapper uses `configs/a2_random3_smoke.yaml`, which only selects
`random3`. It is separate from the generic `run.sh` entrypoint so future full
experiment configs cannot accidentally make the smoke command run
datastores/specbench.

The smoke config runs `baseline`, `ngram`, and `suffix` before MTP methods.
This keeps model-free smoke data from being blocked if a large MTP model hits
an Ascend startup OOM. It also waits briefly after each server cleanup so NPU
memory from the previous vLLM process can be released before the next method
starts.

If some cards are temporarily occupied, use runtime overrides instead of
editing YAML:

```bash
bash run_a2_random3_smoke.sh --tp 6 --npu-devices 2,3,4,5,6,7
```

TP does not have to be a power of two in the runner, but vLLM/model internals
may still reject a TP size if model dimensions cannot be split by that value.
In that case the server log should fail early with a divisibility or tensor
parallel configuration error.

## Step 8. Run The Experiment

Run the default config:

```bash
bash run.sh
```

Run the current random3 smoke test with an automatic preflight first:

```bash
bash run_a2_random3_smoke.sh
```

Run a custom config:

```bash
bash run.sh configs/my_experiment.yaml
```

Resume a stopped run without rerunning successful cases:

```bash
bash run.sh --resume
bash run.sh configs/my_experiment.yaml --resume
```

## Step 9. Read Results

The default output directory is:

```bash
results/a2_random3_smoke/
```

The combined CSV summary is:

```bash
results/a2_random3_smoke/summary.csv
```

Each case also has its own directory:

```text
results/a2_random3_smoke/<case_name>/<timestamp>/
```

Important files in each case directory:

```text
metadata.json       exact commands, env, port, model, dataset, method
bench_stdout.log    vLLM bench stdout/stderr
<case_name>.json    vLLM bench result JSON
```

For single-pass methods, `server.log` is in the same case directory. For
cold/warm suffix methods, both result rows share one server process and one
server log under:

```text
results/a2_random3_smoke/_server_runs/<base_case_name>/<timestamp>/server.log
```

The `summary.csv` columns `base_method`, `phase`, and `server_log` make this
relationship explicit.

## Step 10. Common Changes

Use one NPU:

```yaml
TP: 1
DP: 1
NPU_DEVICES: "0"
```

Use all 8 NPUs for a model:

```yaml
models: [qwen3_32b]

model_catalog:
  qwen3_32b:
    path: /home/huangmy/models/Qwen3-32B
    served_model_name: qwen3-32b
    tp: 8
    dp: 1
    npu_devices: "0,1,2,3,4,5,6,7"
```

Run only datastore experiments:

```yaml
datasets: [datastores384]
```

Run only baseline vs suffix:

```yaml
methods: [baseline, suffix]
```

Use a non-default vLLM binary:

```yaml
VLLM_BIN: /usr/local/python3.11.14/bin/vllm
```

## Notes

- `NPU_DEVICES` uses container-visible device IDs.
- `ASCEND_DEVICE_CHECK` can be `off`, `warn`, or `error`; default is `warn`.
- `--preflight` checks selected model paths, dataset paths, methods, vLLM,
  ports, and visible Ascend devices.
- `--resume` only skips cases with an existing successful result JSON.
- The runner intentionally restarts vLLM for every model/method/dataset case.
